# DECISIONS.md

Ниже зафиксированы ключевые архитектурные решения проекта MushAI. Формат намеренно близок к ADR: **решение**, **почему принято**, **последствия**.

---

## D-001. Базовый execution engine — Magentic-One team

**Статус:** принято

**Решение**

Первая версия MushAI строится вокруг **Magentic-One team runtime**, а не вокруг одного универсального агента.

**Почему**

- Команда агентов лучше соответствует цели проекта, чем одиночный чат-агент.
- Она естественно покрывает поиск, анализ, файлы, код и execution.
- Это создаёт устойчивую основу для будущих modes, subagents и workflows.

**Последствия**

- В центре архитектуры появляется `TeamFactory`.
- Runtime обязан уметь сохранять и восстанавливать состояние команды.
- Все дальнейшие расширения должны быть совместимы с командной моделью.

---

## D-002. Первая версия строится как runtime, а не как бот под конкретный канал

**Статус:** принято

**Решение**

MushAI проектируется как **personal agent runtime**, а не как Telegram-бот, CLI-утилита или Web UI приложение.

**Почему**

- Каналы будут меняться.
- Логика исполнения задач не должна зависеть от формы входа.
- Это защищает проект от раннего lock-in на один transport.

**Последствия**

- Каналы реализуются как adapters.
- Ядро не знает о Telegram-specific или Web-specific деталях.
- Все каналы обязаны использовать единый runtime.

---

## D-003. FastAPI-first как основной ingress layer

**Статус:** принято

**Решение**

В v1 основным ingress layer становится **FastAPI**, а CLI и другие каналы подключаются поверх общей runtime-логики.

**Почему**

- FastAPI упрощает интеграцию внешних transport adapters.
- Позволяет быстро получить рабочий HTTP ingress и health/status endpoints.
- Удобно расширяется в сторону webhook и streaming сценариев.

**Последствия**

- Появляется слой `api/`.
- Определяются стандартные endpoint'ы v1.
- HTTP становится не отдельной реализацией логики, а фасадом над runtime.

## D-004. State-first обязателен уже в v1

**Статус:** принято

**Решение**

Сущности `Session`, `Run`, `Message`, `Checkpoint`, `Artifact` и связанный lifecycle вводятся уже в v1.

**Почему**

- Без этого нельзя нормально поддержать restart recovery.
- Summaries, scheduler и branches зависят от корректной модели state.
- Более поздняя попытка «добавить state поверх хаотичного кода» будет дороже и рискованнее.

**Последствия**

- Persistence — это не optional enhancement, а часть ядра.
- Runtime обязан работать через явный lifecycle сохранения и восстановления.
- Нужно закладывать хранилище и репозитории на раннем этапе.

---

## D-005. Capability registry нужен уже в v1

**Статус:** принято

**Решение**

Даже в первой версии возможности системы оформляются через **Capability Registry**, хотя полноценный capability supply chain переносится на v2.

**Почему**

- Это предотвращает хаотичное врастание tools в runtime.
- Подготавливает основу под будущие tool, subagent и workflow capabilities.
- Упрощает управление доступом и конфигурацией возможностей.

**Последствия**

- В v1 появляется минимальный registry.
- Полноценный self-install и proposal pipeline остаются вне v1.
- Компоненты execution должны обращаться к возможностям через registry, а не через случайные импорты.

## D-006. Исполнение кода — только через Docker sandbox

**Статус:** принято

**Решение**

Выполнение кода и терминальных действий в MushAI должно идти через **DockerExecutionService** или эквивалентную контролируемую песочницу.

**Почему**

- Локальное бесконтрольное выполнение слишком опасно.
- Проект прямо ориентирован на agentic code execution.
- Без песочницы нельзя поддерживать разумный уровень безопасности и управляемости.

**Последствия**

- Нужен workspace lifecycle.
- Нужно хранить результаты исполнения как artifacts.
- Нужно закладывать лимиты, cleanup и execution policies.

---

## D-007. Текущий prototype `magnetic.py` должен быть разобран

**Статус:** принято

**Решение**

Текущий монолитный entry script разбирается на модули.

**Целевые модули**
- `settings/config`
- `prompt rules loader`
- `code executor factory`
- `team factory`
- `team runtime`
- `channels`

**Почему**

- Монолит блокирует развитие архитектуры.
- Смешение transport, prompts, execution и config делает систему хрупкой.
- Для перехода к persistence, scheduler и branches нужна модульность.

**Последствия**

- Первый архитектурный рефакторинг обязателен.
- Новая структура репозитория становится частью v1.

## D-008. Branching в v1 — только как prototype summary-first

**Статус:** принято

**Решение**

В v1 ветвление реализуется как:
- checkpoint fork,
- isolated branch run,
- branch summary,
- возврат summary в main.

Полный merge state не входит в v1.

**Почему**

- Это даёт большую часть пользы side-quests без избыточной сложности.
- Полноценный merge state слишком сложен для ранней версии.
- Summary-first branching помогает держать main context чистым.

**Последствия**

- `BranchManager` в v1 будет ограниченным, но полезным.
- selective merge переносится на v2.5.

---

## D-009. Память v1 — это краткосрочная память и summaries, а не long-term vector memory

**Статус:** принято

**Решение**

В v1 реализуются:
- краткосрочная память,
- summaries,
- context compaction,
- разделение полного trace и condensed context.

Long-term curated memory переносится на v3.

**Почему**

- Long-term memory преждевременно усложнит проект.
- Для v1 критичнее обеспечить чистую рабочую память и restart recovery.
- Summary-based context management даёт практическую пользу уже сейчас.

**Последствия**

- Memory layer в v1 остаётся относительно узким.
- Retrieval-heavy архитектура не блокирует старт ядра.

---

## D-010. Workflow layer в v1 только подготавливается, но не становится основой всей сессии

**Статус:** принято

**Решение**

В v1 система остаётся team-runtime-first. Более формальные execution modes и workflow abstractions появляются начиная с v1.5.

**Почему**

- В ранней версии важнее устойчивое ядро исполнения.
- Graph-centric архитектура слишком тяжела на старте.
- Workflow нужен там, где он действительно полезен, а не как универсальная замена обычной сессии.

**Последствия**

- В v1 не строится graph-first runtime.
- В v1.5 появятся `ExecutionMode`, routing и первые workflows.
- В v2.5 может быть добавлен GraphFlow или аналогичный engine для отдельных deterministic flows.

## D-011. Scheduler входит уже в v1

**Статус:** принято

**Решение**

Scheduler и timed runs входят в первую версию.

**Почему**

- Проект позиционируется как personal runtime, а не только реактивный чат.
- Базовая проактивность нужна уже в ранней версии.
- Scheduler естественно опирается на state-first архитектуру.

**Последствия**

- Нужно вводить `Task model`.
- Scheduler должен генерировать synthetic events в общий runtime.
- Появляется основа для future automations и reminders.

---

## D-012. Observability — обязательная часть v1, а не улучшение “на потом”

**Статус:** принято

**Решение**

В v1 сразу добавляются:
- structured logs,
- trace ids,
- tool execution logs,
- team event logs,
- branch event logs.

**Почему**

- Без этого агентный runtime почти невозможно отлаживать.
- State restoration, scheduler и branching без логов будут непрозрачны.
- Наблюдаемость — это часть надёжности, а не косметика.

**Последствия**

- Нужно проектировать logging с самого начала.
- Run lifecycle должен быть видимым и диагностируемым.

---

## D-013. Self-extension разрешён только через gated pipeline и не входит в v1

**Статус:** принято

**Решение**

Полноценное саморасширение переносится на v2 и должно идти только через контролируемый capability pipeline.

**Почему**

- Нельзя разрешать ядру хаотично дописывать и активировать новые способности.
- Нужны тестирование, policy checks, approval и rollback.
- Иначе проект станет нестабильным и небезопасным.

**Последствия**

- v1 ограничивается registry.
- v2 вводит proposal pipeline, packaging, sandbox checks, approval, activation и rollback.

---

## D-014. Telegram и полноценный Web UI не являются задачами v1

**Статус:** принято

**Решение**

В v1 эти интерфейсы не являются приоритетом и не должны тормозить разработку runtime.

**Почему**

- Преждевременная работа над transport surfaces размоет фокус.
- Сначала надо стабилизировать ядро.
- После этого подключение каналов будет значительно дешевле.

**Последствия**

- CLI и HTTP — первые целевые surfaces.
- Telegram adapter переносится на v3.
- Web UI также переносится на более поздний этап.

---

## D-015. Архитектура должна расти без переписывания ядра

**Статус:** принято

**Решение**

Все решения v1 принимаются с оглядкой на v1.5, v2, v2.5 и v3.

**Почему**

- Проект с самого начала задуман как растущая платформа.
- Нельзя выбирать локально удобные решения, которые сломают capability expansion или workflow maturity позже.

**Последствия**

- Любая новая подсистема должна проходить проверку на расширяемость.
- Важнее правильные границы модулей, чем быстрые временные хаки.

---

## D-016. Основная организационная цель v1 — убрать монолит и собрать вертикальный срез системы

**Статус:** принято

**Решение**

Вместо распыления на множество фич вначале строится вертикальный срез:
- contracts,
- TeamFactory,
- TeamRuntime,
- persistence,
- sandbox,
- adapters,
- logs.

**Почему**

- Вертикальный срез быстрее показывает жизнеспособность архитектуры.
- Он уменьшает риск бесконечной подготовки без работающего runtime.
- Он позволяет раннее end-to-end тестирование.

**Последствия**

- Приоритет отдаётся связности системы, а не количеству функций.
- Порядок работ должен идти от runtime foundation к расширениям.
