# PROJECT_SCOPE.md

## 1. Назначение проекта

**MushAI** — это персональный автономный agent runtime на Python и AutoGen, построенный вокруг **Magentic-One team** как базового execution engine.

Проект создаётся не как очередной чат-бот и не как буквальная копия OpenClaw, а как **расширяемая runtime-система**, которая:

- принимает запросы из разных каналов через единое ядро;
- умеет не только отвечать текстом, но и выполнять действия;
- использует команду агентов для поиска, анализа, работы с файлами, написания и запуска кода;
- безопасно выполняет код в изолированной среде;
- хранит состояние, сессии, результаты и артефакты;
- поддерживает side-quests / branches;
- масштабируется от v1 к v2/v3 без переписывания ядра.

## 2. Главная цель проекта

Построить **надёжный personal agent runtime**, который сначала становится прочной системой исполнения задач, затем системой branching/workflow orchestration, а после этого — контролируемо саморасширяемой платформой capabilities.

## 3. Базовые архитектурные принципы

### 3.1. Transport-agnostic
Telegram, CLI, HTTP, Web UI и любые будущие каналы не являются ядром. Они должны быть только адаптерами поверх единого runtime.

### 3.2. State-first
Состояние, checkpoints, sessions, runs, summaries и branches являются фундаментом системы, а не побочным эффектом реализации.

### 3.3. Capability-driven
Инструменты, подагенты, workflow и будущие расширения рассматриваются как capabilities, а не как хаотично встроенные хардкодные функции.

### 3.4. Sandboxed by default
Код, файловые действия и терминальные операции, которые могут повлиять на систему, по умолчанию выполняются через контролируемую песочницу.

### 3.5. Branch-ready
Архитектура с самого начала проектируется так, чтобы side-quests и ветвление не ломали main session и не загрязняли основной контекст.

### 3.6. Workflow-capable
В дальнейшем система должна поддерживать более формальные execution modes и deterministic workflows, но без превращения всей пользовательской сессии в graph-сценарий.

### 3.7. Self-extensible, but gated
Саморасширение допустимо только как контролируемый pipeline с проверками, approval flow и откатом, а не как произвольная горячая перезагрузка кода.

## 4. Scope версии v1

### 4.1. Что входит в v1

#### Ядро
- FastAPI-first архитектура.
- CLI и HTTP как первые адаптеры.
- Единый runtime для всех каналов.
- Нормализованные контракты `InboundMessage` / `OutboundEvent`.

#### Execution engine
- `MagenticOneGroupChat` как базовая команда.
- Явная сборка команды через `TeamFactory`.
- Базовый состав команды:
  - `WebSurfer`
  - `FileSurfer`
  - `Coder`
  - `Terminal / CodeExecutor`
- Возможность отдельно включать human-in-the-loop, но не как обязательную основу ядра.

#### Состояние
- `Sessions`
- `Runs`
- `Messages`
- `Checkpoints`
- Сохранение и восстановление состояния команды.
- Persistence после рестарта процесса.

#### Инструменты и execution
- Workspace на уровне session/run.
- Docker sandbox для кода.
- Контролируемое файловое окружение.
- Сохранение `stdout`, `stderr`, `exit code`.
- Артефакты выполнения.

#### Память
- Краткосрочная память.
- Summaries и context compaction.
- Отдельное хранение полного trace и condensed context.

#### Организация задач
- `Task model`.
- `Artifact model`.
- Scheduler / timed runs.
- Базовая проактивность через synthetic events.

#### Ветвление
- Прототип `BranchManager`.
- Side-quests через checkpoint fork.
- Возврат branch summary в main line.

#### Наблюдаемость
- Structured logs.
- Trace IDs.
- Tool events.
- Execution events.

### 4.2. Что не входит в v1

В v1 **не входят**:

- Telegram как основной канал.
- Полноценный Web UI как основная точка входа.
- Long-term vector memory.
- Автоматическое саморасширение.
- Marketplace skills.
- Сложные graph workflows.
- Массовая многоагентная маршрутизация вне базового engine.
- Сложный state merge `branch -> main`.

## 5. Результат, который должен дать v1

На выходе v1 MushAI должен быть уже не прототипом, а **рабочим personal agent runtime**, в котором базовая команда умеет:

- искать информацию;
- работать с файлами;
- писать и запускать код;
- использовать терминальную руку через песочницу;
- сохранять и восстанавливать контекст;
- продолжать работу после рестарта;
- работать через несколько точек входа;
- выполнять side-quests без загрязнения main session.

## 6. Границы проекта по версиям

### v1 — Core Runtime
Главная цель: собрать надёжное ядро исполнения задач.

### v1.5 — Structured Execution
Главная цель: добавить execution modes, routing и первые workflow без ломки ядра.

### v2 — Capability Expansion
Главная цель: сделать систему контролируемо расширяемой через capability pipeline.

### v2.5 — Branching & Workflow Maturity
Главная цель: сделать branches и workflow полноценными объектами системы.

### v3 — Mature Autonomous Runtime
Главная цель: получить зрелую автономную систему с несколькими transport adapters, governance и более долгим жизненным циклом.

## 7. Основные ограничения

- Нельзя строить ядро вокруг конкретного мессенджера.
- Нельзя полагаться на небезопасное выполнение команд в локальной оболочке без песочницы.
- Нельзя делать критически важные фичи как набор ad-hoc скриптов без runtime-контрактов.
- Нельзя переносить long-term memory, self-extension и graph-centric architecture в v1 ценой усложнения базового ядра.
- Нельзя смешивать transport layer, execution layer и storage layer в один монолитный entrypoint.

## 8. Нефункциональные требования

### Надёжность
- Система должна переживать рестарт процесса без потери ключевого состояния.
- Повторная обработка входного события должна быть контролируемой через idempotency и run lifecycle.

### Безопасность
- Выполнение кода — только через контролируемую песочницу.
- Capability expansion в будущих версиях — только через gated flow.

### Наблюдаемость
- Любой run должен быть трассируемым.
- Должны существовать event logs, tool logs и branch logs.

### Расширяемость
- Добавление нового канала, capability или workflow не должно требовать переписывания ядра.

## 9. Критерии успеха

Проект движется в правильную сторону, если:

- runtime обслуживает несколько каналов через единое ядро;
- состояние сохраняется и восстанавливается детерминированно;
- агент может выполнять реальные задачи через sandbox;
- ветвление не ломает основную сессию;
- архитектура v1 естественно подготавливает v1.5/v2/v2.5/v3.

## 10. Definition of Done для v1

v1 считается завершённой, если выполнены все условия:

- базовый engine = `Magentic-One team`;
- CLI и HTTP работают через единый runtime;
- state сохраняется и восстанавливается;
- код выполняется в Docker;
- есть workspace и artifacts;
- есть summaries;
- есть scheduler;
- есть prototype branch flow;
- есть logs и tests.
